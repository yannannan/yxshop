# 升级部署与视频依赖策略

日常仍只执行 `bash upgrade.sh`。本轮把升级中的视频步骤固定为只检查已有依赖，不自动安装、下载、编译或更换视频引擎；抖音解析问题按用户要求暂时搁置。

## 源码、项目依赖和视频引擎

| 内容 | 后续升级行为 |
| --- | --- |
| Git 中的项目源码、脚本、锁文件 | 从当前分支的 origin 上游同步；服务器此前确认使用 origin/master |
| node_modules 中的 JavaScript 依赖 | 继续执行 pnpm install --frozen-lockfile --prod=false，缺少锁定的包时可能联网下载 |
| 已安装 yt-dlp、FFmpeg、Firefox、运行记录 | 只检查版本和实际启动，保留现有文件，不自动升级或重装 |
| vendor/video-engine 中的离线文件、缓存 | Git 忽略并保留，不随源码 reset 删除 |
| .env.mysql、.env.local 和上传文件 | 环境文件继续在 reset 前私有备份、之后恢复，上传文件保留 |

当前不是整个项目离线部署。此前两个较大离线包分别提供 yt-dlp 程序和 FFmpeg 签名源码，后者仍需一次本机编译；Firefox 已在服务器安装并通过启动检查。后来的小 tar 包主要是项目源码补丁，不能把这些补丁与已安装的二进制混为一谈。

直接关闭服务器所有网络下载会同时影响 Git 拉代码和项目依赖安装。这里关闭的是日常升级中的视频安装流程，既保留正常发布能力，也避免浏览器偶发自检失败后重新进入 yum、下载或编译。

## upgrade.sh 的行为

1. 先 fetch 并验证当前 origin 上游；缺分支、游离 HEAD 或其他远程配置不停止商城。
2. 验证远程 upgrade.sh 包含 `# video-upgrade-policy: check-only-v1`。旧版入口没有该标记时在停服前退出，避免把本机新版入口覆盖回自动安装版本。
3. 若远程错误跟踪了 vendor/video-engine 中的文件，在停服前拒绝发布，防止用 Windows 或其他机器的引擎覆盖本机 Linux 程序。
4. 保留原环境文件保护、停服、reset 和按锁文件安装项目依赖步骤。
5. 仅调用 `bash scripts/install-video-deps-centos.sh --check` 一次。该分支不进入系统包安装、yt-dlp 下载、FFmpeg 编译或浏览器安装。
6. 视频检查失败时保留现有引擎与缓存，显示具体错误，继续构建并启动商城。项目依赖安装、构建或启动失败仍报错，不能把所有发布错误都视为可忽略的视频错误。

独立视频脚本的默认安装能力仍保留，供明确需要首次安装或人工修复时使用；这属于人工安装操作，可能使用已有离线文件 / 缓存或联网补齐缺少的组件，不会被日常升级自动触发。当前已安装依赖无需重传离线包。

## 首次切换到本轮入口

先将本轮完整项目代码发布到服务器实际跟踪的远程分支。此前服务器的 origin 是本机 Git 服务下的 master，本地 GitHub main 更新不代表该 origin/master 自动更新。助手本轮只提交并合并本地 main，没有推送或更改服务器。

已解压但尚未进入远程仓库的 lib、components 等源码会被原来的 reset --hard 覆盖；不能靠保留旧源码补丁作为长期升级方式。本轮修复应随完整源码发布。vendor/video-engine 的程序和缓存则继续只留在各机器。

第一次在远程同步完成后，先更新入口再运行，避免执行中的旧脚本仍采用旧步骤。以下针对用户已确认的 origin/master，只有验证成功才替换原入口：

```bash
cd /home/www/yxshop/yxshopdev
git fetch origin
task_upgrade_entry="$(mktemp ./upgrade-entry.XXXXXXXX)"
git show origin/master:upgrade.sh > "$task_upgrade_entry" &&
grep -Fx '# video-upgrade-policy: check-only-v1' "$task_upgrade_entry" >/dev/null &&
bash -n "$task_upgrade_entry" &&
chmod --reference=upgrade.sh "$task_upgrade_entry" &&
mv -- "$task_upgrade_entry" upgrade.sh &&
bash upgrade.sh
```

若 grep 未通过，表示远程仍未包含本轮策略，原 upgrade.sh 不会被替换，商城也不会被停止；先完成代码同步，不继续执行旧入口。之后日常只需 `bash upgrade.sh`，没有 pull-only 等第二种升级模式。
