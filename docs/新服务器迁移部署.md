# 新服务器迁移部署

用户确认基础运行环境和 `.env.mysql` 已准备好。新服务器使用 `migration_upgrade.sh`，后续日常升级继续使用现有 `upgrade.sh`；本次没有修改 `upgrade.sh`。

| 入口 | 用途 | 视频依赖行为 |
| --- | --- | --- |
| `bash migration_upgrade.sh` | 新服务器部署，或明确需要执行业务迁移步骤时 | 调用原视频安装脚本；已就绪则复用，缺少时安装 / 下载 / 编译并自检 |
| `bash upgrade.sh` | 现有服务器日常更新 | 只检查现有视频依赖，不自动安装或更换引擎 |

## 执行前准备

- Linux 已准备 Git、Node >=22.13、pnpm，项目已克隆，配置好当前分支的 origin 上游，或者使用 origin 的同名分支。
- 同步本轮完整代码到实际发布源。此前服务器使用自建 Git 的 `origin/master`，本地 GitHub `main` 不会自动同步到这个远程。
- 项目目录有本机 `.env.mysql`，已配置数据库和所需服务密钥。真实环境文件不提交 Git，脚本不会生成真实账号或替换已有 Node。
- 数据库数据、上传附件需事先恢复，或配置继续连接现有数据库 / OSS。当前脚本没有自动跨服务器复制数据库、运行历史 SQL 或修改 Nginx / 证书。
- 视频步骤沿用 `scripts/install-video-deps-centos.sh` 的系统支持范围，当前面向 CentOS 7、Stream 9/10 等该脚本认可的 RHEL 系 x86_64 环境。首次系统依赖安装需要 root；原安装脚本会检查权限。

## 一键执行

在新服务器实际项目目录执行，例如：

```bash
cd /home/www/yxshop/yxshopdev
bash migration_upgrade.sh
```

不需要参数，也不需要另外执行视频安装命令。完整流程：

1. 检查基础命令、Node 版本和本机配置文件。
2. 拉取并验证当前 origin 上游；兼容 main、master 和仓库子目录。检查远程完整迁移入口、日常只检查策略和视频迁移步骤，拒绝远程误跟踪的视频二进制。
3. 私有备份 `.env.mysql` / `.env.local` 后停止商城。
4. `git reset --hard` 同步代码，原样恢复本机配置。与原升级入口一样，会覆盖已跟踪源码的本地修改；Git 忽略的引擎 / 缓存和上传文件保留。
5. `pnpm install --frozen-lockfile --prod=false` 安装项目依赖。
6. 按编号执行 `scripts/migrations/` 中的业务步骤，目前首先调用 `bash scripts/install-video-deps-centos.sh`。
7. 构建生产版本。
8. 使用原 `start.sh` 启动商城。

入口的执行块会先被 Bash 完整解析，避免 reset 更新入口时混读新旧内容；模块列表在同步代码之后读取，本次新增的模块也会执行。

## 失败和重复执行

基础环境、分支或远程验证失败会在停服前退出。代码同步后的项目依赖、迁移、构建或启动失败会返回非零退出码，打印失败阶段，不报告部署成功；已经停止的商城不会自动回滚或恢复启动。

修复问题后重跑同一条 `bash migration_upgrade.sh`。视频步骤使用现有检测 / 缓存逻辑，已就绪时跳过安装；首次缺少依赖仍可能下载、安装系统包和编译 FFmpeg。后续模块也应提供可重复执行的状态检测。

## 扩展其他服务模块

新增 `scripts/migrations/20-模块名.sh`、`30-模块名.sh` 等。入口只执行两位数字编号开头的 `.sh` 普通文件，按文件名顺序运行；README 等说明文件不执行。

成功返回 0，失败返回非 0。前一步失败，后面的模块和构建启动均不继续。模块通过自身路径定位项目，可参考 [迁移步骤说明](../scripts/migrations/README.md)。日常 `upgrade.sh` 不执行这些迁移模块。
